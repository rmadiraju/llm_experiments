Support Agent Design: AWS Bedrock + LangChain/LangGraph

This design describes how to build a production-grade support agent that answers questions using OpenSearch, APIs, logs, and workflow logic. The primary implementation pattern is Bedrock for models and guardrails, LangGraph for orchestration, and LangChain for tool and model integration. A separate optional section shows where Amazon Bedrock AgentCore Runtime fits if you want AWS-managed agent hosting.

Primary Goal

Answer user support questions reliably using evidence from knowledge, operational data, and logs.

Design Principle

Build a workflow-driven agent, not one giant prompt. Keep routing, retrieval, tool usage, and synthesis explicit.

Key Outcome

Responses include grounding, confidence, source attribution, and next actions.

2. Core Responsibilities by Layer

Amazon Bedrock

  • Foundation model inference for intent clarification, retrieval planning, synthesis, and structured extraction.
  • Guardrails for harmful content and sensitive-information protection.
  • Optional use of Bedrock Knowledge Bases if you want managed RAG with citations.

LangChain / LangGraph

  • LangChain for tool wrappers, model interfaces, retrievers, and structured output handling.
  • LangGraph for explicit state, node routing, retries, checkpoints, and human-in-the-loop workflow control.
  • Best fit when support logic spans multiple sources and branches.

  → Intent router

5. Intent Router Design

Routing Strategy

Use a hybrid router:

  • Rules first for obvious patterns such as ticket IDs, claim IDs, deployment IDs, trace IDs.
  • Model classification second for ambiguous or mixed questions.
  • Confidence thresholds determine when to use one path versus multiple paths.
  • Fallback path when confidence is low or access is missing.

Example Intent Output

{
  "intent": "mixed_investigation",
  "confidence": 0.84,
  "entities": {
    "ticket_id": "INC-20491",
    "service": "payment-service",
    "environment": "prod",
    "time_range": "last_4h"
  },
  "sources_needed": ["api", "logs", "kb"]
}

6. Source-Specific Retrieval Strategy

Source Best Used For How To Implement Important Guardrails
OpenSearch / Bedrock KB Runbooks, SOPs, support articles, release notes, prior incident summaries, ticket resolutions Chunk content, enrich with metadata, use hybrid retrieval and filters by product/service/env/version Filter by tenant, product, data sensitivity, freshness
Business APIs Live case status, claim details, order status, workflow state, config state Create typed tools such as get_claim_details, get_ticket_status, get_recent_deployments No generic “call any API” tool; enforce authZ and parameter validation
Logs / Metrics / Traces Incidents, latency, failures, top exceptions, blast radius Use constrained log query tools backed by CloudWatch Logs Insights or observability APIs Redact secrets/PII before model input; enforce time-window bounds
Config / Data Stores Feature flags, routing rules, environment state, support metadata Read through narrow tools and cache selected output in state Avoid direct broad reads from model-generated queries

7. Tool Design Rules

1. Typed Tools Only

Create narrow functions with explicit contracts. Examples: get_ticket_status(ticket_id), query_service_errors(service, env, minutes_back).

2. Result Normalization

Every tool returns compact structured output: summary, key fields, timestamps, identifiers, and safe snippets.

3. Source Labels

Attach a source reference to every retrieved artifact so the final answer can cite where evidence came from.

8. OpenSearch / Knowledge Design

Indexing Model

  • Documents: SOPs, troubleshooting guides, known-error database, release notes, incident reviews.
  • Chunks: 500–1200 tokens, overlap by 10–15% if documents are procedural.
  • Metadata: tenant, product, service, environment, region, doc_type, version, updated_at.
  • Prefer hybrid retrieval: lexical + semantic.

Answering Strategy

  • Retrieve top N chunks.
  • Optionally re-rank if result quality varies.
  • Trim to only the evidence needed for the answer.
  • Return direct source references in the response.

9. Log Investigation Path

Do not send raw log streams to the model. Instead use the model to derive a constrained query plan, execute the query outside the model, and then summarize only the returned evidence.

Example path:
User: "Why did payment retries spike after the 6 PM deploy?"
  → intent = logs_debug
  → extract service=payment-service, env=prod, time_range=last_3h
  → query tool #1: top exceptions by minute
  → query tool #2: latency p95 and error-rate around deployment window
  → API tool: recent deployment details
  → KB tool: known issue article for timeout burst after rollout
  → synthesis: likely cause + confidence + remediation steps

10. Answer Contract

Response Shape

{
  "answer": "Claim updates are delayed because the ingestion worker backlog increased after a configuration change at 18:04 UTC.",
  "confidence": "medium",
  "sources": [
    {"type": "logs", "ref": "cloudwatch:claim-worker-prod"},
    {"type": "api", "ref": "deployment-service:release-8821"},
    {"type": "kb", "ref": "runbook/claim-worker-backlog"}
  ],
  "next_actions": [
    "Scale workers or pause noncritical batch jobs",
    "Verify queue depth reduction over the next 15 minutes"
  ],
  "needs_handoff": false
}

Quality Rules

  • Never pretend certainty when evidence is partial.
  • Separate facts from inferences.
  • Always note the source class behind the answer.
  • Return useful next actions instead of only diagnosis.

11. Security and Governance

Area Control Implementation Guidance
Authentication SSO / IAM / internal identity Pass tenant and user claims to the agent before retrieval or tool use.
Authorization Source-level authorization Restrict tools and retrieval by team, tenant, role, region, and environment.
Safety Bedrock Guardrails Screen prompts and responses, apply denied topics, mask sensitive information.
Secrets Secrets Manager / IAM roles Never expose credentials to the model or prompt payloads.
Auditability Trace each step Store request, intent, selected tools, evidence refs, and final answer metadata.

14. Implementation Plan

Phase 1: MVP

  • 3 intents: docs, API lookup, logs
  • 5–8 narrow tools
  • Basic citations and confidence
  • Single tenant or limited audience

Phase 2: Hardening

  • AuthZ and data filtering
  • Checkpointing and retries
  • Prompt and tool-call observability
  • Human handoff and escalation

Phase 3: Optimization

  • Reranking and retrieval quality tuning
  • Caching hot queries
  • Offline evaluation sets
  • Multi-turn memory and personalization

15. Optional: Where Amazon Bedrock AgentCore Runtime Fits

AgentCore Runtime is optional in this design. Use it when you want an AWS-managed runtime for deploying and operating the agent. It does not replace LangGraph workflow design, retrieval design, or tool design. It sits underneath your agent code as the runtime/hosting layer.

User / UI
API or Direct Invocation
AgentCore Runtime
Managed execution, session handling, scaling
LangGraph Agent App
Your router, tools, synthesis, checkpoints
Data Sources
OpenSearch, APIs, logs, KB, stores

Use AgentCore Runtime When

  • You want AWS-managed runtime deployment instead of operating ECS/EKS yourself.
  • You need secure access to VPC-connected internal APIs and data.
  • You want runtime-level sessions, invocation patterns, and operational metrics.
  • You expect the agent to move from prototype to production quickly on AWS.

Skip It Initially When

  • You are still iterating heavily on graph design and tool contracts.
  • You already have a container platform and deployment standards.
  • You want to validate workflow quality before optimizing hosting.

How To Add AgentCore Runtime to This Design

Integration Steps

  1. Build the support agent as a standard LangGraph application first.
  2. Externalize config, policies, model selection, and endpoints.
  3. Package the app for AgentCore Runtime deployment.
  4. Configure runtime permissions and VPC connectivity to internal APIs, OpenSearch, and observability systems.
  5. Expose invoke endpoints to your chat UI or API gateway.
  6. Add runtime metrics, traces, and alerting.

What Stays the Same

  • LangGraph nodes and state model
  • Tool wrappers and API contracts
  • Bedrock model usage and guardrails
  • Retrieval quality tuning
  • Response format and business safety rules

16. Practical Recommendation

Start with Bedrock + LangGraph + direct tools. Get the router, retrieval plan, source grounding, and answer quality right first. Then decide whether to host the agent on your existing platform or move it to AgentCore Runtime for managed AWS operation. This keeps the architecture clean: LangGraph is the agent brain and workflow; AgentCore Runtime is the hosting shell.
