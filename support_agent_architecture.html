Enterprise Support Agent
Architecture & Implementation

A production-grade, workflow-driven support agent that answers questions using knowledge bases, business APIs, logs, and operational data. Built on Amazon Bedrock for LLM inference and guardrails, LangGraph for stateful orchestration, and LangChain for tool and retriever integration — designed for multi-tenant enterprise deployment.

Design Principles
⚡

Workflow-Driven

Explicit state machine — not one giant prompt. Routing, retrieval, tool use, and synthesis are separate, testable stages.

🔍

Evidence-Grounded

Every answer cites its source — KB article, API response, or log query. Confidence levels are always surfaced.

🏢

Multi-Tenant Safe

Tenant isolation at every layer: retrieval filters, tool authorization, data scoping, and guardrail policies.

📈

Scalable by Design

Stateless compute, checkpointed state, async tool execution, and horizontal scaling across all layers.

Section 2

Core Responsibilities by Layer

Amazon Bedrock

  • LLM inference — intent classification, entity extraction, retrieval planning, answer synthesis, and structured output generation.
  • Embeddings — Titan Embeddings for vector search in OpenSearch or Bedrock Knowledge Bases.
  • Guardrails — content screening, denied-topic enforcement, PII masking, and hallucination grounding checks.
  • Knowledge Bases (optional) — managed RAG with automatic chunking, indexing, and citation-aware retrieval.

LangGraph / LangChain

  • LangGraph — explicit state graph, conditional routing between nodes, checkpointing, retries, timeouts, and human-in-the-loop breakpoints.
  • LangChain — model interfaces (ChatBedrock), tool wrappers, retrievers (OpenSearchVectorSearch), structured output parsers, and prompt management.
  • State management — typed state object flows through the graph; every node reads/writes specific fields.
  • Observability — LangSmith or OpenTelemetry tracing for every node, tool call, and LLM invocation.
Section 3

End-to-End Request Flow

1
Normalize & Authenticate

Clean input, resolve session, attach tenant context, enforce rate limits. Rewrite ambiguous queries if multi-turn context clarifies intent.

2
Classify Intent

Hybrid router: regex/keyword rules fire first for obvious patterns (ticket IDs, deployment refs). LLM-based classification handles ambiguous queries. Returns intent label + confidence score.

3
Extract Entities

Pull structured fields: service name, environment, region, time range, ticket/claim/order IDs, user identifiers. These parameterize downstream tool calls.

4
Plan Retrieval Strategy

Based on intent + entities, select which data sources to query: KB only, API only, logs only, or multi-source. Set parallel vs. sequential execution order.

5
Execute Tools & Gather Evidence

Run typed tool calls against OpenSearch, business APIs, and log query services. Each tool returns normalized evidence with source labels and timestamps.

6
Rank & Trim Evidence

Score evidence by relevance, recency, and authority. Optionally apply a cross-encoder reranker. Trim to the top-K most useful pieces to stay within context limits.

7
Synthesize Answer

LLM generates a grounded response using only the gathered evidence. Output includes: answer text, confidence level, source citations, and recommended next actions.

8
Apply Guardrails & Policy

Bedrock Guardrails screen the response. Custom policy engine checks for unauthorized data disclosure, off-topic drift, or low-confidence situations requiring escalation.

9
Deliver or Escalate

Return the response with citations. If confidence is below threshold or the query requires human judgment, route to the escalation queue with all gathered context.

Section 5

Intent Router — Detailed Design

Hybrid Routing Strategy

The router uses a two-pass approach for speed and accuracy:

  • Pass 1 — Rule engine: Regex patterns detect ticket IDs (INC-\d+), claim refs, deployment hashes, trace IDs. These map directly to api_lookup or logs_debug intents with high confidence.
  • Pass 2 — LLM classification: For queries that don't match rules, send to Bedrock with a classification prompt. Returns intent + confidence. If confidence < 0.7, trigger a mixed_investigation path that queries multiple sources.
  • Fallback: If confidence < 0.4 or intent is unsupported, route to human handoff with the gathered context.

Intent Taxonomy

IntentDescriptionPrimary Source
docs_kbHow-to, process, SOP, FAQ questionsOpenSearch / Bedrock KB
api_lookupStatus checks, account/order/claim infoBusiness APIs
logs_debugIncident investigation, error analysisCloudWatch / Log indices
mixed_investigationComplex queries needing multiple sourcesAll sources
generalGreetings, clarifications, meta questionsLLM only
unsupportedOut-of-scope, needs humanHandoff

Enterprise tip: Start with 4–5 intents maximum. Measure misclassification rates with an eval set before adding new intents. Each new intent increases routing complexity and testing burden.

Section 7

Tool Design Principles

Typed & Narrow

Every tool has an explicit contract with typed inputs and outputs. No generic "execute_api" or "run_query" tools. Each tool maps to one business capability.

# Good
get_ticket_status(ticket_id: str)
query_error_rate(
  service: str,
  env: str,
  minutes_back: int
)

# Bad — too generic
call_api(url: str, params: dict)

Normalized Output

Every tool returns a standard evidence envelope: summary, key fields, timestamps, identifiers, and a source label for citation tracking.

{
  "source": "api:ticket-service",
  "ref": "INC-20491",
  "timestamp": "2026-03-31T14:22Z",
  "summary": "Ticket open, P2...",
  "data": { ... }
}

Defense in Depth

Tools enforce their own guardrails independent of the orchestrator: parameter validation, AuthZ checks, timeout enforcement, output size limits, and PII redaction before returning data to the LLM.

  • Max result size per tool: configurable
  • Timeout: 5–30s per tool call
  • Retry policy: exponential backoff, max 2
  • Circuit breaker: fail open with cached data or graceful degradation
Section 8

OpenSearch / Knowledge Base Design

Indexing Pipeline

  • Documents: SOPs, troubleshooting guides, known-error database, release notes, incident reviews, past ticket resolutions, product documentation.
  • Chunking: 500–1200 tokens per chunk. 10–15% overlap for procedural documents. Section-aware splitting — don't break mid-procedure.
  • Metadata per chunk: tenant, product, service, environment, region, doc_type, version, updated_at, author, data_classification.
  • Embeddings: Amazon Titan Embeddings V2. Batch-generate on ingest, store alongside text in OpenSearch knn_vector field.
  • Refresh strategy: Event-driven (Confluence webhook → Lambda → reindex) + nightly full sync as safety net.

Retrieval Strategy

  • Hybrid search: Combine BM25 lexical with kNN vector. Weight tuning: start at 60% semantic / 40% lexical, adjust per domain.
  • Metadata pre-filtering: Always filter by tenant. Add service, environment filters when entities are extracted. Dramatically reduces noise.
  • Top-K retrieval: Fetch top 15–20 chunks, then rerank to top 5–8 for the synthesis prompt.
  • Reranking (optional): Use a cross-encoder model or Bedrock reranker for quality-critical deployments.
  • Freshness boost: Score recently updated documents higher. Critical for fast-moving knowledge like incident runbooks.
Section 9

Log Investigation Pipeline

Critical rule: Never send raw log streams to the model. Use the model to derive a constrained query plan, execute the query outside the model, and summarize only the returned evidence.

Example Investigation Flow

User: "Why did payment retries spike after the 6 PM deploy?"

Step 1 — Intent: logs_debug
Step 2 — Entities: service=payment-svc, env=prod, time_range=last_3h
Step 3 — Tool #1: query_top_exceptions(service, env, minutes=180)
         → Returns: TimeoutException surged at 18:04 UTC
Step 4 — Tool #2: query_latency_metrics(service, env, percentile=p95)
         → Returns: p95 jumped from 220ms to 4800ms at 18:03
Step 5 — Tool #3: get_recent_deployments(service, env, hours=4)
         → Returns: Release v2.14.0 deployed at 17:58 UTC
Step 6 — Tool #4: search_kb("timeout burst after rollout payment")
         → Returns: Known issue KB-4421 — connection pool exhaustion
Step 7 — Synthesis: Likely cause identified + confidence: high
         → Answer: connection pool not resized for new retry logic
         → Next actions: rollback or hotfix pool config

Response Schema

     "ref": "runbook/claim-backlog"}

    "Scale workers or pause batch jobs",
    "Monitor queue depth for 15 min"
  ],
  "needs_handoff": false,
  "metadata": {
    "latency_ms": 2340,
    "tools_called": 3,
    "evidence_count": 7
  }
}

Quality Rules

  • No fabricated certainty: If evidence is partial, say so. Use confidence levels: high, medium, low, insufficient.
  • Separate facts from inferences: Clearly distinguish "logs show X" from "this likely means Y."
  • Always cite sources: Every factual claim links to a source type and reference.
  • Actionable next steps: Don't just diagnose — recommend what to do next.
  • Escalation trigger: Auto-handoff when confidence < threshold, when the query involves billing/legal, or when the user explicitly asks for a human.
  • Tone consistency: Professional, concise, empathetic. Match the enterprise's voice guidelines.

13.2 — Intent Router Node

# app/graph/nodes/router.py
import re, json
from langchain_aws import ChatBedrock
from langchain.prompts import ChatPromptTemplate

llm = ChatBedrock(
    model_id="anthropic.claude-3-sonnet-20240229-v1:0",
    region_name="us-east-1",
    model_kwargs={"temperature": 0, "max_tokens": 256}
)

# ── Pass 1: Rule-based fast path ──
RULE_PATTERNS = {
    "api_lookup": [
        (re.compile(r"INC-\d+", re.I), 0.95),
        (re.compile(r"CLM-\d+", re.I), 0.95),
        (re.compile(r"ORD-\d+", re.I), 0.93),
    ],
    "logs_debug": [
        (re.compile(r"trace[_-]?id", re.I), 0.90),
        (re.compile(r"(error|exception|spike|latency|timeout)", re.I), 0.80),
    ],
}

def rule_classify(question: str) -> tuple[str, float] | None:
    for intent, patterns in RULE_PATTERNS.items():
        for regex, conf in patterns:
            if regex.search(question):
                return intent, conf
    return None

# ── Pass 2: LLM classification ──
CLASSIFY_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """Classify the support question into exactly one intent.
Intents:
- docs_kb: how-to, process, SOP, FAQ questions
- api_lookup: status checks, account/order/claim info lookups
- logs_debug: incident investigation, error/latency analysis
- mixed_investigation: complex queries needing multiple sources
- general: greetings, meta questions, clarifications
- unsupported: out-of-scope, needs human

Return JSON: {"intent": "...", "confidence": 0.0-1.0}
Return ONLY the JSON, nothing else."""),
    ("human", "{question}")
])

def classify_intent(state: AgentState) -> dict:
    question = state["normalized_question"] or state["question"]

    # Try rules first
    rule_result = rule_classify(question)
    if rule_result:
        return {"intent": rule_result[0], "intent_confidence": rule_result[1]}

    # Fall back to LLM
    chain = CLASSIFY_PROMPT | llm
    raw = chain.invoke({"question": question}).content.strip()
    parsed = json.loads(raw)
    return {
        "intent": parsed["intent"],
        "intent_confidence": parsed["confidence"]
    }

13.3 — Entity Extraction Node

# app/graph/nodes/entities.py
ENTITY_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """Extract structured entities from this support question.
Return JSON with these optional fields:
  service, environment, region, time_range, ticket_id, claim_id, deployment_id
If a field is not mentioned, omit it.
Return ONLY valid JSON."""),
    ("human", "{question}")
])

def extract_entities(state: AgentState) -> dict:
    chain = ENTITY_PROMPT | llm
    raw = chain.invoke({"question": state["normalized_question"]}).content
    parsed = json.loads(raw)
    return {"entities": Entity(**parsed)}

13.4 — OpenSearch Retrieval Node

# app/graph/nodes/retrieve_kb.py
from opensearchpy import OpenSearch

os_client = OpenSearch(
    hosts=[{"host": "your-domain.us-east-1.es.amazonaws.com", "port": 443}],
    use_ssl=True,
    http_auth=("user", "pass"),  # or use IAM auth via requests_aws4auth
)

def retrieve_kb(state: AgentState) -> dict:
    entities = state.get("entities") or Entity()
    question = state["normalized_question"]

    # Build metadata filters
    filters = [{"term": {"tenant_id": state["tenant_id"]}}]
    if entities.service:
        filters.append({"term": {"service": entities.service}})
    if entities.environment:
        filters.append({"term": {"environment": entities.environment}})

    # Hybrid search: BM25 + kNN vector
    body = {
        "size": 15,
        "query": {
            "bool": {
                "must": {"match": {"content": question}},
                "filter": filters
            }
        },
        "knn": {
            "embedding": {
                "vector": get_embedding(question),  # Titan Embeddings
                "k": 15,
                "filter": {"bool": {"must": filters}}
            }
        }
    }
    results = os_client.search(index="support-docs", body=body)
    
    evidence = []
    for hit in results["hits"]["hits"]:
        evidence.append(Evidence(
            source_type="kb",
            source_ref=f"opensearch:{hit['_index']}/{hit['_id']}",
            content=hit["_source"]["content"],
            relevance_score=hit["_score"],
            timestamp=hit["_source"].get("updated_at")
        ))
    
    return {"evidence": state["evidence"] + evidence}

13.5 — Answer Synthesis Node

# app/graph/nodes/synthesize.py
SYNTH_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """You are an enterprise support agent. Answer the question 
using ONLY the evidence provided. Follow these rules:

1. Cite sources using [source_ref] notation
2. State confidence: high / medium / low / insufficient
3. Separate facts from inferences
4. Provide actionable next steps
5. If evidence is insufficient, say so clearly

Evidence:
{evidence}

Return JSON:
{
  "answer": "...",
  "confidence": "high|medium|low|insufficient",
  "sources_used": ["ref1", "ref2"],
  "next_actions": ["action1", "action2"],
  "needs_handoff": false
}"""),
    ("human", "{question}")
])

def synthesize_answer(state: AgentState) -> dict:
    evidence_text = "\n\n".join(
        f"[{e.source_ref}] {e.content}"
        for e in state["ranked_evidence"]
    )
    chain = SYNTH_PROMPT | llm
    raw = chain.invoke({
        "evidence": evidence_text,
        "question": state["normalized_question"]
    }).content
    
    result = json.loads(raw)
    return {
        "answer": result["answer"],
        "confidence": result["confidence"],
        "sources": [{"ref": s} for s in result["sources_used"]],
        "next_actions": result["next_actions"],
        "needs_handoff": result.get("needs_handoff", False)
    }

13.6 — Graph Assembly

# app/graph/graph.py
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver
from .state import AgentState
from .nodes import (
    normalize, router, entities, planner,
    retrieve_kb, call_apis, query_logs,
    rank_evidence, synthesize, guardrails, handoff
)

def build_graph():
    graph = StateGraph(AgentState)

    # ── Add nodes ──
    graph.add_node("normalize", normalize.normalize_request)
    graph.add_node("classify_intent", router.classify_intent)
    graph.add_node("extract_entities", entities.extract_entities)
    graph.add_node("plan_retrieval", planner.plan_retrieval)
    graph.add_node("retrieve_kb", retrieve_kb.retrieve_kb)
    graph.add_node("call_apis", call_apis.call_support_apis)
    graph.add_node("query_logs", query_logs.query_logs)
    graph.add_node("rank_evidence", rank_evidence.rank_and_trim)
    graph.add_node("synthesize", synthesize.synthesize_answer)
    graph.add_node("guardrails", guardrails.apply_guardrails)
    graph.add_node("handoff", handoff.handoff_to_human)

    # ── Linear flow through normalize → classify → extract ──
    graph.set_entry_point("normalize")
    graph.add_edge("normalize", "classify_intent")
    graph.add_edge("classify_intent", "extract_entities")
    graph.add_edge("extract_entities", "plan_retrieval")

    # ── Conditional: fan out to data sources ──
    graph.add_conditional_edges(
        "plan_retrieval",
        planner.route_to_sources,
        {
            "kb_only": "retrieve_kb",
            "api_only": "call_apis",
            "logs_only": "query_logs",
            "multi": "retrieve_kb",  # starts parallel fan-out
            "handoff": "handoff",
        }
    )

    # ── Converge into ranking → synthesis → guardrails ──
    graph.add_edge("retrieve_kb", "rank_evidence")
    graph.add_edge("call_apis", "rank_evidence")
    graph.add_edge("query_logs", "rank_evidence")
    graph.add_edge("rank_evidence", "synthesize")
    graph.add_edge("synthesize", "guardrails")

    # ── Final: deliver or escalate ──
    graph.add_conditional_edges(
        "guardrails",
        guardrails.check_policy,
        {"pass": END, "fail": "handoff"}
    )
    graph.add_edge("handoff", END)

    # ── Compile with checkpointing ──
    checkpointer = MemorySaver()  # swap for DynamoDB saver in prod
    return graph.compile(checkpointer=checkpointer)

        "error": None,
    }
    
    config = {"configurable": {"thread_id": thread_id}}
    result = await agent.ainvoke(initial_state, config)
    
    return {
        "answer": result["answer"],
        "confidence": result["confidence"],
        "sources": result["sources"],
        "next_actions": result["next_actions"],
        "needs_handoff": result["needs_handoff"],
        "thread_id": thread_id,
    }

Section 17

Optional: Amazon Bedrock AgentCore Runtime

Use AgentCore Runtime When

  • You want AWS-managed runtime instead of operating ECS/EKS
  • You need secure VPC access to internal APIs and data
  • You want built-in session management and scaling
  • You're moving from prototype to production quickly on AWS

Skip It Initially When

  • You're still iterating on graph design and tool contracts
  • You already have container infrastructure and CI/CD
  • You want to validate workflow quality before optimizing hosting
  • You need capabilities not yet supported by the runtime

Recommendation: AgentCore Runtime is a hosting shell — it does not replace your LangGraph design, tools, or retrieval logic. Start with Bedrock + LangGraph + your own compute. Add AgentCore when you're ready to optimize operations.

Section 18

Cost Optimization Strategies

Model Tiering

Use a smaller/cheaper model (Haiku, Titan Lite) for intent classification and entity extraction. Reserve the larger model (Claude Sonnet/Opus) for answer synthesis only. This can reduce LLM costs by 40–60%.

Caching Layers

Cache OpenSearch results for identical queries (Redis, 5–15 min TTL). Cache API tool responses for stable data (ticket status doesn't change every second). Use Bedrock prompt caching for repeated system prompts.

Smart Routing

Short-circuit obvious queries with the rule-based router — no LLM call needed. For FAQ-style questions with high semantic similarity to cached answers, return cached responses directly.

Section 19

Testing & Evaluation Framework

Unit Tests (Per Node)

  • Intent router: 100+ labeled queries → expected intent + confidence range
  • Entity extraction: 50+ queries → expected entity fields
  • Tool wrappers: Mock API responses, verify parameter validation, output normalization, error handling
  • Synthesis: Given fixed evidence, verify answer quality, citation accuracy, confidence calibration

End-to-End Evaluation

  • Golden dataset: 200+ question → expected answer pairs covering all intents
  • Metrics: Intent accuracy, entity F1, answer relevance (LLM-as-judge), citation precision, latency P95
  • Regression: Run eval suite on every PR. Block deployment if metrics drop below threshold.
  • Shadow mode: Run new versions alongside production, compare outputs before cutover.
