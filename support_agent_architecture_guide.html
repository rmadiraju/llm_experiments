Architecture Guide

Support Agent Architecture and Implementation Guide

A detailed design for a support agent that knows what questions to ask, when to use documentation, when to call APIs, how to gather evidence, and how to decide what action can be taken.

Build this as a triage + investigation + resolution system, not just a chatbot.

1. Core Idea

The agent should follow this sequence:

  1. Understand what kind of issue the customer is facing.
  2. Determine what information is missing.
  3. Ask only the minimum next question needed.
  4. Gather evidence from documentation, APIs, logs, ticket history, and configuration sources.
  5. Reason over the evidence and decide the likely cause, recommended steps, and whether an action or escalation is needed.
  6. Respond in a structured support format.
The support agent is best thought of as an issue-handling workflow engine with LLM reasoning on top.

2. Issue Handling States

State Purpose Example
Intake Capture the customer problem in natural language. "My deployment failed", "Repo was not created", "Why is onboarding stuck?"
Issue Classification Map the problem to an issue family and subtype. Pipeline failure, onboarding issue, release issue, permissions issue
Missing Info Detection Identify required fields before investigation can continue. Environment, component name, request ID, pipeline run ID
Evidence Collection Use docs, APIs, logs, and monitoring to gather facts. Query pipeline API, fetch logs, search KB articles
Reasoning and Decision Determine cause, confidence, safe next step, and whether escalation is needed. Known policy gate failure with high confidence
Response Generation Return summary, findings, likely cause, actions, and next steps. Explain root cause and give the exact remediation steps

3. Recommended Logical Architecture

Customer / Support User
  -> Support UI / Chat
    -> Conversation Orchestrator
      -> Issue Router
      -> Slot Filler / Question Planner
      -> Investigation Planner
      -> Tool Executor
          -> Docs Search
          -> Product APIs
          -> Logs / Metrics APIs
          -> Ticketing APIs
          -> Action APIs
      -> Policy / Guardrail Engine
      -> Answer Composer
    -> Structured Response

Conversation Orchestrator

Owns session state, controls flow, stores case context, and decides the next step.

Issue Router

Classifies issue type and subtype from customer language and conversation context.

Slot Filler / Question Planner

Tracks missing fields and asks the next highest-value question instead of asking everything at once.

Investigation Planner

Chooses tools and defines the sequence of lookups needed to diagnose the issue.

Tool Executor

Provides a controlled layer for docs search, APIs, logs, tickets, and action calls.

Policy / Guardrail Engine

Controls permissions, evidence requirements, escalation conditions, and safety of actions.

4. Three-Layer Brain Design

Layer 1: Intent / Issue Router

Identifies the issue category, subtype, urgency, missing fields, and candidate tools.

{
  "issue_category": "pipeline_failure",
  "subcategory": "build_error",
  "urgency": "medium",
  "needs_clarification": true,
  "missing_fields": ["component_name", "pipeline_run_id", "environment"],
  "suggested_sources": ["pipeline_api", "build_logs_api", "kb_ci_cd"]
}

Layer 2: Slot Filling / Question Planner

This layer decides what to ask next. It should be config-driven, not invented fresh every time by the model.

{
  "issue_type": "pipeline_failure",
  "required_fields": [
    "component_name",
    "environment"
  ],
  "optional_fields": [
    "pipeline_run_id",
    "branch",
    "error_message",
    "timestamp"
  ],
  "question_priority": [
    "component_name",
    "environment",
    "pipeline_run_id",
    "error_message"
  ],
  "tool_dependencies": {
    "pipeline_api": ["component_name", "environment"],
    "build_logs_api": ["pipeline_run_id"]
  },
  "stop_when": [
    "enough_context_for_pipeline_lookup",
    "user_declines_more_details"
  ]
}

Layer 3: Investigation / Action Planner

Once enough context is available, choose tools in order, correlate evidence, and decide safe next steps.

  1. Call pipeline status API.
  2. Fetch latest failed stage.
  3. Fetch stage logs.
  4. Retrieve KB articles matching the failure signature.
  5. Correlate with recent config or policy changes.
  6. Generate probable cause and recommended action.

5. Use Issue Playbooks Instead of Raw Prompting

Each issue family should have a playbook that defines symptoms, required inputs, data sources, rules, allowed actions, and escalation conditions.

issue_type: release_issue
symptoms:
  - "release failed"
  - "cannot promote"
  - "approval blocked"
required_inputs:
  - app_name
  - environment
optional_inputs:
  - release_id
  - approver_group
tools:
  - release_api
  - approval_api
  - environment_status_api
knowledge_sources:
  - release_runbook
  - approval_policy_doc
decision_rules:
  - if approval status is pending -> explain approver requirement
  - if artifact missing -> direct to pipeline artifact validation
  - if policy gate failed -> show failed policy and remediation
allowed_actions:
  - retry_check
  - draft_ticket
  - generate_runbook_steps
escalation:
  - if production blocked and no safe self-service action exists
Playbooks make the system reliable, testable, auditable, and much easier to scale.

Category Used For Examples

Operational System Context Current status, workflow progress, provisioning state, release or deployment status Onboarding API, pipeline API, release API, GitHub API, AppConfig API

7. Decision Logic: Ask User vs Docs vs API

Ask the user when

  • Required identifiers are missing.
  • The symptom maps to multiple possible issue families.
  • Live lookup requires a request ID, component name, or environment.
  • The available evidence is insufficient for a safe conclusion.

Use docs when

  • The user is asking how something works.
  • The question is process or policy oriented.
  • A known error signature maps directly to a documented runbook.

Use APIs when

  • The question depends on current system state.
  • The issue is about a real failure or a current incident.
  • You need tenant, app, environment, pipeline, release, or provisioning status.

Use both when

  • You diagnose from APIs or logs and explain the fix from docs or runbooks.

8. Case Context Object

Every support conversation should build and update a structured case context.

{
  "case_id": "CASE-12345",
  "issue_type": "onboarding_issue",
  "subcategory": "repo_not_created",
  "customer": "TenantA",
  "app_name": "claims-service",
  "environment": "dev",
  "request_id": "ONB-9981",
  "symptoms": [
    "repo missing after onboarding"
  ],
  "collected_facts": [
    "onboarding submitted at 2026-04-11T10:15:00Z",
    "infra completed",
    "repo creation step failed"
  ],
  "missing_fields": [],
  "tool_results": {
    "onboarding_api": "...",
    "github_provisioning_api": "..."
  },
  "likely_cause": "GitHub org permission mapping missing",
  "recommended_actions": [
    "re-run repo provisioning",
    "validate GitHub team mapping"
  ],
  "confidence": 0.87,
  "escalation_needed": false
}
This object is the backbone for consistency, observability, replay, testing, and audit.

9. Config-Driven Questioning Model

Do not hardcode all conversational behavior in prompts. Store issue metadata and question logic as configuration.

{
  "issue_catalog": [
    {
      "issue_type": "onboarding_issue",
      "match_terms": ["onboarding", "setup", "provision", "repo not created"],
      "required_fields": ["app_name", "component_type"],
      "optional_fields": ["request_id", "tenant_id", "environment"],
      "questions": {
        "app_name": "Which application or component are you onboarding?",
        "component_type": "Is this a microservice, UI app, batch job, or something else?",
        "request_id": "Do you have the onboarding request ID?"
      },
      "tool_preconditions": {
        "onboarding_api": ["app_name"],
        "repo_api": ["app_name"]
      }
    }
  ]
}
Capability Why It Matters
Required fields Prevents investigation from starting with missing identifiers
Question priority Ensures the agent asks only the most valuable next question
Tool preconditions Prevents invalid or premature API calls
Stop conditions Controls when the agent should stop asking and start investigating
Match terms and symptoms Improves classification and fallback matching

10. Orchestration Flow

  1. Classify the issue.
  2. Load the matching playbook or issue definition.
  3. Compare case context against required fields.
  4. Ask one targeted follow-up question if needed.
  5. When minimum fields are collected, call the relevant APIs and systems.
  6. Search docs or runbooks using failure signatures and live evidence.
  7. Generate summary, findings, likely cause, and recommendations.
  8. Offer a safe action or escalate if needed.
User: "My stage release is blocked"

Agent:
1. Ask: "Which application or service is this for?"
2. Ask: "Is this for dev, stage, or prod release flow?"
3. Call release API, approval API, and policy gate API
4. Detect that artifact signing policy failed
5. Search runbook for the exact policy failure
6. Return likely cause, remediation steps, and confidence

11. Tool Registry Design

Each tool should be typed, declared, permissioned, and self-describing.

{
  "tool_name": "pipeline_status_api",
  "purpose": "Get latest pipeline run status",
  "required_inputs": ["component_name", "environment"],
  "mode": "read",
  "risk": "low"
}
{
  "tool_name": "retry_repo_provisioning",
  "purpose": "Retry failed repo provisioning",
  "required_inputs": ["request_id"],
  "mode": "write",
  "risk": "medium",
  "approval_required": true
}
Field Purpose
purpose Explains what the tool is for
required_inputs Used by the question planner and validator
mode Distinguishes read-only from action-taking tools
risk Used by policy engine and approval flow
approval_required Prevents unsafe automatic actions

12. Standard Response Format

Do not return only a large paragraph. Use a support-oriented structured format.

What I found
The onboarding request for claims-service completed infrastructure setup, but the GitHub repository creation step failed.

Likely cause
The GitHub team mapping for this tenant appears to be missing, which blocked repo provisioning.

What you can do now
Validate the team mapping in onboarding settings and retry provisioning.

Recommended next step
I can help by checking the onboarding request details or generating the exact remediation steps.

Confidence
High

13. Action and Escalation Decisioning

Outcome Type When to Use Examples
Self-Service Answer User can resolve the issue with clear instructions Known policy gate fix, access request steps, onboarding documentation
Assisted Support Action Agent can safely trigger or prepare an action Retry lookup, rerun validation, draft ticket, notify team
Human Escalation Confidence is low, action is risky, or prod issue needs manual handling Conflicting evidence, production outage, missing permissions, unknown failure

When escalating, the agent should generate a complete summary:

  • Issue type and customer problem statement
  • Identifiers such as tenant, app, environment, run ID, request ID
  • Evidence already collected
  • Likely cause and confidence
  • Actions already attempted

14. Guardrails

  • Evidence-first rule: never claim a root cause without evidence from tools or runbooks.
  • Action safety rule: no write action unless policy, role, and confidence checks all pass.
  • Clarification threshold: ask when required fields are missing instead of guessing.
  • Evidence traceability: store which tool or doc produced each fact.
  • Confidence scoring: compute confidence from data completeness, source agreement, and issue-match quality.
The most dangerous failure mode is confident hallucination about a live operational issue. Keep the system evidence-driven.

Area Suggested Option Why

16. Recommended MVP

Start with these issue types

  • Onboarding issue
  • Pipeline failure
  • Release issue
  • Access / permission issue

MVP capabilities

  • Issue classification
  • Missing-field detection
  • Single-question stepwise clarification
  • Docs search
  • 3 to 5 read-only API integrations
  • Structured answer generation
  • Escalation summary generation

Delay these until later

  • Too many issue categories
  • Broad unrestricted tool use
  • Autonomous write actions in production
  • Complex multi-agent behavior before core flow works

17. Example End-to-End Interaction

User: "My stage release is blocked"

Agent: "Which application or service is this for?"
User: "claims-api"

Agent: "Is this in dev, stage, or prod?"
User: "stage"

Agent actions:
- Call release API
- Call approval API
- Call policy gate API
- Detect artifact signing failure
- Search runbook for signing failure

Response:
What I found:
The release exists and approval is complete, but promotion to stage is blocked by the artifact-signing policy gate.

Likely cause:
The artifact produced by the pipeline is missing the required signature.

What you can do now:
Check the signing stage of the build pipeline and verify that the artifact signing job completed successfully.

Recommended next step:
I can generate the exact remediation checklist or prepare an escalation summary.

Confidence:
High

18. What to Define Before Coding

  • Issue taxonomy
  • Issue playbook schema
  • Question / slot schema
  • Tool registry schema
  • Case context schema
  • Response template schema
  • Action policy matrix
  • Escalation policy matrix
These artifacts matter more than coding the first prompt. They determine system reliability.

19. Final Design Principle

Do not build "an LLM that answers support questions."

Build a support case orchestrator that uses an LLM for classification, questioning, reasoning, and explanation.

That difference is what makes the system operationally useful.
